# Decision: reactive 6-DoF pose controller ported from the simulation

2026-07-24. The simulation's reactive pose controller (msc_project
`controller/reactive_controller.py`: PD on pose+twist error → damped
least squares → null-space joint centering) is ported into `basic_control`
as a second control law, `--controller reactive-pose`, alongside the
unchanged `resolved-rate` default.

This is the return of task-space control that
`reactive-control-removal.md` (2026-07-17) left the door open for — but as
a pure `Controller` implementation inside the hardened framework, not a
revival of the removed 1 kHz velocity-mode path. Everything that made the
2026-07-17 attempt fault is now owned by the framework: position-mode
actuation with client-side integration, seed-from-measured takeover
(T1-T6), per-joint clamp at 0.9× model limits, the 3° following-error
guard, non-finite/saturation/overrun counters, and no auto-resume after a
fault.

## What lives where

- `src/control/ReactiveLaw.h` — the equations, header-only and pure Eigen
  (mirrors the simulation file: pose error, twist error, task twist, DLS,
  null-space). No Kortex, no Pinocchio: testable anywhere.
- `src/control/ReactivePose.{h,cpp}` — binds the law to the `Controller`
  interface: FK + full 6×7 `LOCAL_WORLD_ALIGNED` Jacobian from the SAME
  measured q (`pose_and_jacobian`, math/Kinematics), measured end-effector
  twist = J·q̇_measured, pose targets from `PoseTargetStore`.
- `src/control/Target.{h,cpp}` — `ParsePoseTarget` / `PoseTargetStore` /
  `RunPoseTargetInput`: stdin lines of `x y z` (meters, base frame;
  orientation target kept) or `x y z roll pitch yaw` (radians,
  R = Rz(yaw)·Ry(pitch)·Rx(roll) — the simulation's convention).
- Telemetry: `rot_error_rad` (rotation-log error norm) joins `sigma_min`
  in `ControllerStatus`, the log sample, and the CSV — orientation
  convergence must be provable from the data, not eyeballed.

## Equation fidelity — how "the same controller" is proven

`tests/test_reactive_law.cpp` (portable, in `ctest` everywhere) checks the
C++ law against fixtures generated by `scripts/gen_reactive_fixtures.py`
from the ACTUAL Python simulation law: identical inputs (Jacobian, errors,
q, gains, term flags) must produce identical `qdot_raw` to 1e-12. The
fixtures header is checked in; regenerate only when the simulation law
changes.

## Deliberate deviations from the simulation

1. **Damped null-space projector.** The sim projects with an undamped
   pseudoinverse `(I − J⁺J)`; near singularities that is ill-conditioned
   exactly where DLS is protecting the task term. The port uses
   `N = I₇ − Jᵀ(JJᵀ + λ²I₆)⁻¹J` with the same λ as the DLS. (The fixture
   for this case uses λ = 1e-8, where both agree to 1e-6.)
2. **Centering wrap.** Kortex reports joint positions in [0, 360); the
   centering error is `remainder(q − q_mid, 2π)` so a joint at 350° pulls
   −10°, not −350°. MuJoCo's q is continuous — the sim never needed this.
3. **Centering mask.** Gen3 joints 1/3/5/7 are continuous and have no
   midpoint: masked out (`config::kNullCenteringMask` = {0,1,0,1,0,1,0},
   midpoints 0°). Caution: this arm has CONFIGURED soft limits far inside
   the URDF range (joint 4 ≈ −19.6°, joint 6 ≈ +36°) — verify with
   `./query_limits` before enabling centering.
4. **log3 via Eigen.** `e_rot` comes from `Eigen::AngleAxisd` (angle·axis),
   mathematically identical to Pinocchio's `log3` (fixture-verified incl.
   near-π) but dependency-free, keeping the law portable.
5. **Gains are NOT the simulation's.** The sim runs Kp_pos = 32 /s at
   500 Hz with perfect zero-latency feedback. On hardware that would
   saturate the velocity clamp on any few-cm error (per-joint clamping
   destroys the DLS direction — the documented 2026-07-17 failure mode)
   and outrun the 3° following-error guard. Defaults start at the
   hardware-proven resolved-rate scale: Kp_pos = `kp` = 1.0 /s,
   Kp_rot = 1.0 /s, λ = 0.1. Any ramp is its own evidence-backed step.
6. **Speed clip** stays the framework's 0.9× model limits (the sim clips
   at 1.0×); the sim's ±0.2 rad command-lead clamp is NOT ported — the
   3° following-error guard covers runaway between command and
   measurement, by stopping rather than silently clamping.

## Staged bring-up (each stage gated on the previous one's CSV)

Configuration, not code: `orientation_enabled` (default true),
`velocity_term_enabled` (Kd, default OFF), `null_space_enabled`
(default OFF) — TOML/CLI via app/Options.

1. Hardware machine: full build; `ctest` all green (incl. the fixture
   cross-check).
2. Read-only: startup FK-vs-robot report; `./query_limits` (speed limits
   match the model; note the configured J4/J6 position limits).
3. P-only hold: takeover, no target typed — no drift, clean teardown,
   `rot_error_rad`/`sigma_min` in the CSV.
4. Single-axis 2–5 cm position steps — convergence ≈ Kp·error, no
   saturation, following error ≪ 3°.
5. Small orientation-only step (≤ 0.1 rad about one axis) —
   `rot_error_rad` converges, position holds.
6. Enable `velocity_term_enabled`, repeat 4–5 (Kortex velocity feedback is
   noisier than MuJoCo's — watch for chatter).
7. Optionally enable `null_space_enabled` (after re-checking the
   configured limits); only then consider gain ramping.

Success means frames, units, timing, equations, safety behaviour, and
convergence are verified from the logs — not that the arm moved. The
arrival notice is position-based (like resolved-rate); orientation
convergence is judged from `rot_error_rad`, not the notice.
